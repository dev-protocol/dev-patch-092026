# Path B (EIP-7702) Operational Feasibility Assessment

## 1. Feasibility on Mainnet — Feasible (Proven)

- Since Pectra, EIP-7702 is live on mainnet. **The attacker is already using 7702 in production**
  (`0xBBa56874` `0x58d3382f` `0xe9084b1b` carry `0xef0100||delegate` code).
- The owner EOA `0x1dCb85ef…` is a **clean EOA with no code** (`cast code` = `0x`, nonce 6231,
  balance 0.0261 ETH). It is in a state where a new delegation can be attached.
- Foundry `cast` fully supports 7702: `cast wallet sign-auth` (authorization signing) / `cast send --auth`.

## 2. Concrete Procedure for Executing `settleAsOwner()` via 7702 (cast, proven)

Flow **actually executed successfully** on a local anvil fork (`status 1 (success)`, gasUsed 149,142,
pair burn → supply 15.838B → 12.754B, factory restored within the same TX):

```bash
# Variables
CONFIG=0x1D415aa39D647834786EB9B5a333A50e9935b796
ORIGF=0xCD82603e66F30162cfc1aE3770510480464F5275   # marketFactory to restore
PAIR=0x4168CEF0fCa0774176632d86bA26553E3B9cF59d
SETTLEMENT=<deployed Settlement address>
MAX=0xffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff

# The owner EOA attaches a 7702 delegation "to itself" and executes settleAsOwner in one TX
#   Passing the delegate (Settlement) via --auth makes cast sign the authorization and temporarily
#   point the EOA's code at the Settlement implementation. The call target is the EOA itself, so
#   address(this)==msg.sender==owner.
cast send $OWNER_EOA \
  --auth $SETTLEMENT \
  --private-key $OWNER_KEY --rpc-url $RPC \
  "settleAsOwner(address,(address,uint256)[],address[])" \
  $ORIGF "[($PAIR,$MAX), (0x58d3...,$MAX), (0x4a5d...,100000000000000000000000000)]" "[$PAIR]"
```

### Sponsor-Separated Variant (NOT SUPPORTED — see note above)

> ⚠️ **Not compatible with `settleAsOwner` as currently implemented.**
> The contract enforces `require(msg.sender == address(this))`, which only holds when the owner EOA
> itself submits the TX (self-sponsored). In the sponsor-separated variant, `msg.sender` is the
> relayer, not the owner EOA, so `settleAsOwner` reverts. Hardware wallet operators must use
> **Path A** (deployed-factory, 3 TX) instead. The procedure below is retained for documentation
> of the EIP-7702 standard capability, but is **not executable** against the current contract.

Signing (owner key) and gas payment (relayer key) can be separated:

```bash
# 1) The owner signs only the authorization offline (nonce = owner's current nonce)
AUTH=$(cast wallet sign-auth $SETTLEMENT --private-key $OWNER_KEY --nonce <owner_nonce> --chain 1)
# 2) A separate relayer EOA pays gas and sends. The `to` is the owner EOA, with the signed auth attached
cast send $OWNER_EOA --auth $AUTH --private-key $RELAYER_KEY --rpc-url $RPC \
  "settleAsOwner(address,(address,uint256)[],address[])" $ORIGF "<targets>" "[$PAIR]"
```

### Revoking the Delegation (mandatory after execution)
A 7702 delegation **persists on the EOA after the TX** (proven: after execution, `cast code` = `0xef0100||Settlement`).
Leaving it in place is dangerous. Revoke by re-authorizing to the zero address:

```bash
cast send $OWNER_EOA --auth 0x0000000000000000000000000000000000000000 \
  --private-key $OWNER_KEY --rpc-url $RPC $OWNER_EOA
# Afterwards confirm cast code $OWNER_EOA == 0x (proven)
```

## 3. Risk Assessment

| Risk | Description | Mitigation |
|---|---|---|
| **Delegation persistence** | 7702 code does not vanish after one TX; it persists. If left, anyone can call that implementation with owner privileges | Revoke with `--auth 0x0` immediately after execution. Make the completed revocation a closing condition of the operational procedure |
| **Delegate swap / re-entry** | If the implementation is malicious or swappable, owner privileges can be fully hijacked | Settlement is immutable (no privilege changes outside the constructor). Verify the implementation after deployment and double-check the address passed to `--auth` |
| **Third-party submission of the authorization** | A signed authorization can be submitted on-chain by anyone once the nonce is valid (cast warns about this) | Assign the authorization nonce immediately before sending and consume it yourself right away. Never let an unused authorization circulate |
| **State on TX failure** | `settleAsOwner` executes register→burn→sync→deregister→restore atomically in one TX. A mid-way failure fully reverts (the factory is restored too). However, **the delegation-code attachment itself may succeed and persist** | Even on failure, check `cast code`, and if the code remains, always revoke with `--auth 0x0` |
| **Hardware wallet support** | Ledger/Trezor support for 7702 authorization signing depends on firmware/app and is still maturing | Sponsor-separated variant is incompatible with `settleAsOwner`'s `msg.sender == address(this)` guard. Use **Path A** for hardware wallets |
| **Nonce contention** | With self-sponsoring, the authorization nonce must be handled as tx nonce+1. cast handles this automatically, but manual auth requires care | Self-sponsored: cast handles it automatically. Manual: assign `--nonce` for sign-auth precisely |

## 4. Path A (3 TX) vs Path B (1 TX) — Practical Comparison and Recommendation

| Aspect | Path A: deployed factory | Path B: 7702 owner delegate |
|---|---|---|
| TX count | 3 (setMarketFactory → settle → restore) | 1 (fully atomic) |
| Owner-key usage | setMarketFactory ×2 only (settle uses a separate executor key) | Owner key signs settleAsOwner (when self-sponsored) |
| Intermediate-state exposure | **A window of minutes or more during which the factory points at our contract** (addGroup is possible during that window) | Intermediate state exists only within the TX (not observable externally) |
| Failure recovery | Each TX is independent. Even if settle fails, executing restore separately recovers. Verifiable step by step | Full revert is safe, but the persistent delegation code requires cleanup |
| Ease of verification | Each TX can be individually pre-simulated and confirmed | Behavior is condensed into a single TX. Prior `cast call`/fork verification is mandatory |
| Key management | Owner key and executor key can be separated, minimizing owner-key exposure | The execution TX is issued with the owner key (self-sponsored only; sponsor-separated is blocked by the msg.sender guard) |
| Code attached to owner EOA | None (the owner remains a plain EOA) | Temporarily attached + must be revoked (persistence risk) |

**Recommendation: Path A (3 TX) is the first choice for production.** Reasons:
- Owner-key exposure is limited to the two setMarketFactory calls, and the actual burn is executed with a separate executor key
  (a good fit for hardware-wallet operation, avoiding the uncertainty of 7702 hardware-signing support).
- Each TX can be simulated and confirmed individually, and staged recovery is easy on failure.
- No cleanup risk from persistent delegation code.

**Path B is the alternative when "no intermediate state may be exposed at all" or "single-TX atomicity is the top priority".**
Even then, use self-sponsored execution with the owner key, and include the
post-execution `--auth 0x0` revocation as a completion condition of the procedure. If the requirement to minimize the
intermediate-state risk (the factory window) is strong, there is room to choose B, but A remains the default
recommendation for its simplicity in key handling and cleanup. For hardware wallet operators who cannot self-sponsor, Path A is the only option.
